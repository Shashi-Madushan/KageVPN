# Audit, October 2026

An audit of Kage VPN (branch `dev`) for correctness and reliability, the fixes made during it, what is still open, and feature ideas backed by what users of similar apps report.

**Short version.** The code base is in good shape (152 tests passing, no type errors, clean architecture). The audit found two ways the app could close itself, one way it could replace a user's servers with an empty list, one way a normal-looking setting made every connection fail on blocked networks, an IPv6 route gap, and a number of smaller reliability problems. All of those are fixed and covered by tests (see the verification line below). The largest remaining risk is architectural (the root helper trusts files a user-level process can write) and is described under [Still open](#still-open).

Nothing here is committed. The changes sit in the working tree on `dev` so they can be reviewed first.

## How it was checked

- Read the connection path end to end: `session.rs`, `runner/` (including both shell scripts), `config.rs`, `health.rs`, `reliability.rs`, `network_watch.rs`, `store.rs`, `subscriptions.rs`, `core/`, `downloads.rs`, `app_update.rs`, the five protocol parsers, usage, logs, the front-end store, release scripts.
- Baseline before changing anything: `cargo test` 152 passed, `svelte-check` 0 errors, `npm audit` 3 low (dev tooling only; 0 after the small-items round).
- Every suspected bug was **reproduced before it was fixed** (a failing test, or a command run against real sing-box), and every fix has a regression test. Two ideas were tested and **turned out wrong**; they are noted so nobody chases them again (see "Disproved" below).
- The configuration tests run the real `sing-box check` (sing-box 1.14.2 is installed here).
- The live tunnel on this Mac was only inspected read-only (routes, process list, file sizes). All experiments ran on spare ports with their own files.

After the work: `cargo test` 219 passed, `cargo clippy --all-targets -- -D warnings` clean, `svelte-check` 0 errors, release-script tests 9 passed, `vite build` succeeds.

Severity: **High** loses data, stops connections for a group of users, or can end the app. **Medium** degrades reliability or trust. **Low** is polish.

## Fixed

| # | Sev. | Problem | Evidence | Fix |
|---|---|---|---|---|
| F1 | High | The app could close itself (and drop the VPN) on a server link containing non-ASCII text in `pcs=`. Release builds use `panic = "abort"`, and the parser sliced the text by byte offset. A subscription holding such a link would also crash the app at every launch, because the scheduler refreshes at startup. | Failing test: "end byte index 2 is not a char boundary". | Only ASCII hex is accepted. A mutation fuzz test now feeds 60,000 damaged links through all five parsers; it was checked to fail on the old code. |
| F2 | Medium | The crash log, written at the moment something else has already failed, cut itself at a raw byte offset and could panic once it passed 200 KB with non-ASCII text in it. | Failing test. | Cuts at a character boundary. |
| F3 | High (rare) | If the data file existed but could not be read (permissions, failing disk), the store started empty and the migration step then saved over the user's servers. Also: one server this version cannot parse (for example a protocol added by a newer build) made the whole file "corrupt" and moved every server, subscription and setting aside. | Failing tests. | Unreadable files are moved aside (or, if even that fails, saving is refused with a clear message). Unknown servers are kept verbatim under `unreadableProfiles` and return when readable; the rest loads normally. A file from a newer schema is backed up before an older build saves over it. |
| F4 | High | **Country lists made connections fail on blocked networks.** sing-box downloads rule-sets itself and refuses to start if the first download fails. The app pointed it at GitHub. On a network that blocks GitHub (the main reason to need a VPN) every connect failed once a list was on. The option used (`download_detour`) is also deprecated in sing-box 1.14 and **removed in 1.16**, which would break every user with a list after an engine update. | Reproduced with real sing-box: `FATAL initialize rule-set ... connection refused`, exit after 1 s. 1.14.2 prints the deprecation warning. | New `rulesets.rs`: the app downloads each list (GitHub, then a jsDelivr copy), checks it really is a rule-set file (a hotel sign-in page is rejected), writes it atomically and gives sing-box local files. A list that cannot be fetched is left out with a notification; the connection still starts. Old lists refresh in the background after a week; a list that just failed is not waited for again by reconnect attempts. Verified: sing-box starts in 1 s with local lists and no network, with no warnings. |

(This Mac's network has no IPv6, so a real leak could not be shown, only the missing routes.) | The TUN has the documented dual-stack address pair. | F7 | Medium | The health check used one address (`cp.cloudflare.com`). If that single site was blocked or down, a working tunnel was shown as "no internet" and, with *Restart a dead tunnel* on, was restarted. | Code read; tests with local servers. | Three unrelated sites are tried in turn; a healthy tunnel still costs one request. |
| F8 | Medium | A custom DNS entry lost everything after the host. A personal DoH link such as `https://dns.nextdns.io/<id>` silently asked the anonymous endpoint instead. An invalid entry silently turned into "system resolver". | Test; the old code is visible in `config.rs`. | Scheme, port and path are kept (`https`, `tls`, `quic`, `udp`, `tcp`). An invalid entry is refused on save. All eight shapes pass real `sing-box check`. |
| F9 | Medium | When saving a setting failed, the screen still changed and said "Routing saved." | Code read (`run()` swallowed errors). | `attempt()` only updates the screen when the backend call succeeded. Applied to ten settings actions. |
| F10 | Medium | Downloads could hang forever when the connection dropped (engine install, release list), holding the one-download-at-a-time lock, and Cancel did not work while stalled. | Test with a server that goes silent: it hung before; it ends in under 5 s now. | Shared body reader with stall detection and cancel polling; connect and response timeouts; the app-update download got a stall watchdog. |

| F12 | Medium | Import: a name with unencoded spaces (`#My Server`) was cut to `My`; a first link after an invisible byte-order mark was dropped; `tuic://`, `hysteria://`, `wireguard://` and others vanished silently. | Tests. | Names keep their spaces, several links on one line still split, the BOM is ignored, and unsupported schemes are reported (`tuic:// links are not supported yet`). | F13 | Low–Medium | The "subscription expired" notification repeated on every refresh (every 12 h) forever. A new sing-box release that rejects one of our settings now fails CI first. Clippy is clean, so the gate can be strict. |

### Fixed afterwards (the small items)

| # | Sev. | Problem | Fix |
|---|---|---|---|
| F19 | Low–Medium | Disconnect did nothing while the connection was still starting (hotkey, menu, deep link, quit), and the interface blocked the button entirely. | A cancel flag is checked between the steps of connecting (rule lists, server check, helper start, readiness wait). The mascot and the menu-bar item become **Cancel** while connecting, with a short guard so a double-click on Connect does not cancel itself. A cancel is never reported as a failure, and the reconnect loop treats it as the user taking over. |
| F20 | Low–Medium | After a slow stop (up to 10 s of waiting), the app showed "disconnected" while sing-box still held port 2080, and the next connect failed with "port already in use". | If the port is busy within a minute of the app stopping sing-box, the next connect waits up to 10 s for it to be released. A port held by something else still fails straight away. |
| F21 | Low | A subscription refresh saved back a copy taken before the download, undoing any change made meanwhile. If the subscription was removed during the download, its servers were added back as orphans nobody could delete. | The entry is read again after the download and only the refresh's own fields are updated; a subscription removed meanwhile is reported and adds nothing. |
| F22 | Low | A subscription that kept failing was retried every 30 minutes for ever. | Retries back off (30 min, 1 h, 2 h, ... up to the normal interval) and the first success resets them. |
| F23 | Low | Provider placeholder rows ("Remaining traffic ...", pointing at `127.0.0.1` or `0.0.0.0`) were imported as servers. | Loopback and unspecified addresses are skipped when a subscription is imported, with the reason shown; a server on a private LAN address is still accepted. Old placeholder rows disappear on the next refresh. |
| F24 | Low | `npm audit` reported 3 low findings (`cookie` 0.6 inside SvelteKit). | An `overrides` entry moves `cookie` to 0.7.2, which keeps the two functions SvelteKit uses. 0 findings; `svelte-check` and the build pass. |

### Disproved

- **"The 15 s update-check timeout also caps the app download."** A test showed the plugin hands the download no timeout at all (`timeout: None`), so this does not happen. The real gap was the opposite (a stalled update download could hang), which F10 covers.
- **"`sing-box check` reports deprecations."** It does not; only `sing-box run` prints them, so the check-based tests would not have caught F4. CI will not either. Worth re-running `sing-box run` on a generated config after each engine release.

## Still open

Ordered by risk. None of these were changed because each needs a design decision or something this session could not test.

**O1. Root helper trusts files a user-level process can write (High, architectural).** The root service and the per-launch helper run sing-box as root with `config.json` and `helper.start` from the user's data folder. In the per-launch mode the helper script and the sing-box binary also live there. Any process running as the user can therefore make a root process run what it chooses. In per-launch mode it can swap `helper.sh` or the sing-box binary while the password prompt is open, which is arbitrary code as root. In both modes it can change the configuration, so root sing-box does what the file says (for example writing log files anywhere through `log.output`, or redirecting all traffic). Fixing only the script leaves the configuration route open. This is a design weakness, not a demonstrated exploit; nothing was attempted against the live service. The real fix is a signed privileged helper (`SMAppService` plus XPC) that builds the configuration itself from a validated description. That needs the Apple Developer ID the roadmap already lists for notarization.

**O2. The kill switch is reactive and has gaps (Medium).** (a) It engages only after the helper notices sing-box died (0.5 s poll) and never when sing-box is alive but the tunnel is broken. (b) A failed reconnect attempt writes the `stop` file, which releases the firewall block, so traffic is unprotected after the first failed attempt while the app says "could not reconnect". Simply keeping the block would break reconnecting, because the pre-connect DNS check is itself blocked for users with a public resolver. (c) Server IPs are resolved once with the system resolver; sing-box may resolve a CDN-fronted name to different addresses and be blocked. (d) IPv6 neighbour discovery is not allowed. A redesign should keep a persistent allow-list that is refreshed, skip the DNS pre-check while it is up, and release only on an explicit disconnect. ExpressVPN made the same change for the same reason (see sources).

**O3. ~~Debug logging keeps a record of destinations~~ — done (Medium, privacy).** Settings → Logs now has *Errors only* (`warn`), *Normal* (`info`, the new default) and *Detailed* (`debug`), plus *Clear logs when disconnected*. Checked against sing-box 1.14.2: `info` and `debug` both log every destination, `warn` only the ones that failed, so *Normal* is not private; only *Errors only* and the clear switch are. Original finding: The log level is fixed at `debug`; the last two runs' worth of visited hosts stay in `sing-box.log` and `.prev`. That sits badly with "usage recording can be turned off". Add a log-level setting (default Normal) and clear logs on disconnect as an option. Keeping `debug` was a deliberate choice to diagnose silent exits, so make it a toggle rather than removing it.

**O4. ~~Fixed local ports~~ — done (Medium).** Connecting prefers 2080 and 19090 and takes the next free port when another program holds them (a sing-box this app stopped a moment ago is still waited for). The chosen port is used by the health, diagnostics, traffic, subscription and controller code and shown on the Home page in Proxy Only mode. Original finding: `2080` (mixed inbound) and `19090` (API) are constants. Another sing-box app or a second copy makes connecting fail with "port already in use". Needs a free-port pick passed to the health, diagnostics and tray code that all read `MIXED_PORT`.

**O5. The dead-tunnel restart is off by default (Low–Medium).** One of the most-discussed problems in the nearest comparable app is its core silently stopping (see sources), and users there asked for exactly this watchdog. With F7 the false-positive risk is lower, so consider turning it on for new installs.

**O6. Smaller items still open.**
- The local proxy on `127.0.0.1:2080` has no password, so any local user can use the tunnel. A password would break *Proxy Only* mode, where people type the address into other apps by hand; it needs an opt-in setting.
- Release builds are produced for the host CPU only, while the README promises Apple Silicon and Intel. No release has been published yet. A universal build (`tauri build --target universal-apple-darwin`, after `rustup target add x86_64-apple-darwin`) would fix it, but it changes the release script and has to be tried on the machine that builds releases.

## Needs a manual check

These changes are correct as far as the code and automated tests can show, but the environment they matter in was not available.

1. **IPv6 (F5).** On a network with IPv6: connect in TUN mode, then `netstat -rn -f inet6 | grep utun` should show `::/1` and `8000::/1` through the tunnel; `curl -6 https://api64.ipify.org` should return the tunnel's exit address, and ordinary sites should still load. If a server has no IPv6, apps should fall back to IPv4 without a long delay. If that delay is noticeable, add an "IPv6" setting (see ideas) instead of removing the fix.
2. **Blocked GitHub (F4).** Block `raw.githubusercontent.com` (a `/etc/hosts` entry is enough), turn on a country list in Rules mode, delete `~/Library/Application Support/com.apzur.kage/rule-sets/`, and connect. Expect the jsDelivr copy to be used, or a notification and a working connection if both are blocked.
3. **Root service prompts (F14).** After installing this build over an existing service, the first TUN connect should show one password prompt and then work; a declined prompt should not stop the connection.
4. **Kill switch (O2).** Untouched; test before relying on it.

## Feature ideas

Ranked by how much the evidence supports them. **Strong** means a vendor or tracker states it; **Moderate** means it is inferred from comparable apps; **Idea** has no direct evidence.

1. **Per-app picker for bypass/proxy rules. Strong.** Split tunneling is the most requested macOS VPN feature: PIA reports more than 20,000 request tickets for it and Proton made it the headline of its 2025 roadmap. Kage already supports app-name rules and already lists the apps using traffic, but the user has to type an executable name. Add a picker (installed apps, or "add a rule" on a row of the Connections page). Effort: small to medium, front-end mostly.
2. **A kill switch that stays up while reconnecting. Strong.** See O2; ExpressVPN's latest macOS update did exactly this.
3. **Connect or switch mode by network, without reading the Wi-Fi name. Moderate.** "Auto-connect on untrusted Wi-Fi" is a standard setting, but since macOS 14 reading the SSID needs Location permission and a user-session app (a root service cannot), and sing-box's own tracker has SSID-detection bugs. sing-box already logs the default gateway and its hardware address, which identify a network without any permission.
4. **"Repair" and diagnostics for when the engine or service misbehaves. Strong.** One of Clash Verge's most-discussed issues (100 comments) is the core randomly dying, with a core downgrade as the usual workaround; after macOS 26.1 users lost the TUN interface and the fix was reinstalling the service. Kage has the crash log and engine manager; add a one-click *Repair VPN service* (F14's reinstall, on demand), mark the last engine version that worked so it can be rolled back, and export a redacted diagnostics bundle to a file (the redaction already exists for feedback).
5. **More protocols and subscription formats. Moderate.** Hiddify accepts sing-box, V2Ray, Clash and Clash Meta subscriptions and runs TUIC, Hysteria, SSH and WireGuard. F12 now reports which schemes were skipped, so the demand in real subscriptions can be measured before choosing. Each protocol is one module (`docs/ADDING-A-PROTOCOL.md`).
6. **Low-data and expiry alerts in the menu bar. Moderate.** Hiddify shows remaining days and traffic, and one of its open issues is a wrong "expired" state, so people rely on this. Kage already parses the provider's usage header; F13 covers expiry, so add a 90% data warning and show remaining days in the popover.
7. **IPv6 and logging settings. Idea, inferred from F5 and O3.** A server without IPv6 may make some apps slow to fall back, so an "IPv6: through the tunnel / off" switch gives users a way out of F5 without losing the fix for everyone else. Pair it with O3 so privacy-minded users can pick a quiet log level.
8. **System-proxy mode. Moderate.** In Clash Verge "cannot enable the system proxy" has 16 comments, so many users rely on it instead of TUN. It needs a restore-on-crash step so a dead app never leaves a dead proxy configured.
9. **Free-port handling (O4).** Not requested anywhere I found, but a plain failure for anyone running another sing-box app.
10. **Native NetworkExtension mode. Moderate, long term.** Hiddify has an open request for it, and sing-box's own Apple apps use it. It would remove the need for the root helper (O1) and allow on-demand connection. Requires the Apple Developer Program.
11. **Opt out of App Nap while connected. Low.** Hiddify's macOS issue is about an in-process core; Kage's core is a separate process, so only the health and reconnect timers could be delayed. Hold an activity assertion while connected; needs a small Objective-C binding.
12. **Ideas without direct evidence:** scan a QR code from the screen or a dropped image, a server switcher in the menu-bar popover, a universal (Intel and Apple Silicon) release build.

## What the research could and could not show

Web searches were thin on direct complaints about this exact kind of app. The strongest material came from issue trackers (Clash Verge Rev, Hiddify, sing-box) and vendor announcements. Where a point rests on those, it is marked Strong or Moderate above; anything inferred is marked as such. Reddit and App Store reviews were not covered.
